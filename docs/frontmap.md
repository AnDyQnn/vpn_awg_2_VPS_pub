# Карта экранов бота

Обзор всего, что человек видит, нажимая кнопки: какие экраны есть, какие на них
кнопки, куда каждая ведёт. Отдельно для администратора и для клиента.

**Открыть:** [`docs/assets/frontmap.html`](assets/frontmap.html) — просто двойным
щелчком, обычным браузером. Ни сервера, ни сборки, ни сети не нужно.

## Два вида

**Ветка** — то, что открывается сразу. Три колонки: откуда сюда ведут · где вы
стоите · куда отсюда можно уйти. Щелчок по соседней карточке переносит вас туда,
сверху копится путь, по которому вы шли, — и по нему можно вернуться на любой
шаг назад.

Так и ходит по боту живой человек: экран за экраном. Экранов больше двухсот, и
показать их разом значит показать кашу — двести карточек и полтысячи линий
читаются не лучше белого шума.

Связи при этом живые: у выбранного экрана исходящие горят синим и бегут по ходу
движения, входящие — фиолетовым и против хода. Наведите на кнопку — подсветится
именно её линия, ещё до щелчка. Щелчок по заголовку текущего экрана сворачивает
и разворачивает список кнопок.

Колонка «сюда ведут» показывает первые восемь: на «Администрирование» ведёт
кнопка возврата почти с каждого экрана, и список «откуда сюда можно попасть»
почти всегда «отовсюду». Остальные — по требованию.

**Вся карта** — общий вид: колонками по глубине, карточки свёрнуты, линии
приглушены. Нужен, чтобы увидеть форму целиком и найти оторванные куски. Порядок
внутри колонки считается по родителям, поэтому соседи по смыслу оказываются
соседями на экране.

**Обновить после правок в боте:**

```
python docs/assets/build_frontmap.py
```

---

## Откуда берутся данные

Из самого кода. Сборщик читает `VPS_RU/bot/*.py`: находит объявления
`InlineKeyboardButton`, достаёт подпись и `callback_data`, а потом разбирает
роутер `bot.py` и связывает каждую кнопку с обработчиком, который за ней стоит.
Результат кладётся в `docs/assets/frontmap.data.js`; **руками его не правят** —
он перезаписывается.

Карта, нарисованная руками, врёт на второй день: кнопку переименовали, экран
добавили, ветку убрали — а на картинке всё по-старому. Такая карта хуже
отсутствующей, потому что ей верят.

Роутер бота разложен четырьмя способами сразу, и сборщик знает все:

| Как написано в `bot.py` | Пример |
| --- | --- |
| точное сравнение | `if data == "svc_menu": await service_menu(...)` |
| по приставке | `if data.startswith("user_detail_"): ...` |
| списком | `if data in ["menu_ru_server", "menu_de_server"]: ...` |
| таблицей | `actions = {"gen_key": generate_key_request, ...}` |

Плюс разбираются псевдонимы импорта: `common_screen as flt_common` — и в
роутере, и на карте это один и тот же экран.

## Чего карта честно не знает

- **Подписи и адреса, собранные на лету.** `f"🟢 Онлайн · {n}"` зависит от
  данных: постоянная часть показана, переменная — многоточием. Выдумывать
  значение нельзя, поэтому такие кнопки помечены.
- **Шаги мастеров**, нарисованные прямо в роутере (выдача ключа: срок → DNS →
  привязка Telegram), отдельной функции не имеют. Они показаны как узлы с
  пометкой «шаг» — иначе ветка обрывалась бы на полпути.

## Что видно на карте, кроме самих экранов

- **«не дойти»** — экран есть в коде, но от главного меню до него не добраться
  ни одной цепочкой кнопок. Включается галочкой «недостижимые».
- **«ветки в роутере нет»** — кнопка нарисована, а обработчика для её
  `callback_data` не нашлось. Нажатие не сделает ничего. Именно так жила мёртвая
  кнопка «Фильтры».
- **«меню»** — клавиатура собирается в `ui.py` и показывается несколькими
  обработчиками сразу. Такие кнопки видно на каждом экране, который их
  показывает.

## Имена кнопок — плоский конфиг

`config/buttons.json` — единственное место, где задаются подписи:

```json
{
  "gen_key": "🔑 Новый ключ",
  "svc_menu": "⚙️ Админка"
}
```

Ключ — `callback_data`, то есть адрес нажатия. Значение — то, что увидит
человек. Чего в файле нет — остаётся как в коде.

Править можно руками или мышью в карте: щёлкнуть по подписи, написать своё,
затем «Мои правки → Сохранить файлом» и положить полученный `buttons.json` в
`config/`. Бот читает его при запуске — **код трогать не нужно**, достаточно
обычной выкладки.

Адрес нажатия один на весь проект, поэтому переименование действует на всех
экранах, где эта кнопка нарисована. Сколько их — написано прямо под кнопкой на
карте. Это не побочный эффект, а смысл: «🔙 Главное меню» должно называться
одинаково везде.

Кнопки, у которых адрес собирается на лету (`act_pause_<ключ>`), настроить
нельзя — постоянного ключа у них нет. Такие на карте не редактируются.

Сломанный или отсутствующий файл бота не роняет: он скажет об этом в журнале и
возьмёт подписи из кода.

## Что остаётся наброском

Порядок кнопок, переносы между экранами, положение карточек. Плоским словарём
это не выразить: порядок живёт в коде рядом с условиями вроде «эту строку
показываем, только если есть Xray». Такие правки карта показывает списком,
переносить их нужно руками.

Хранится всё в браузере (`localStorage`) — привязано к машине и профилю.

## Проверка, что карта открывается

Страница — такой же код, только сломается она молча: откроешь файл, увидишь
пустоту и решишь, что «что-то с браузером». Поэтому есть прогон в настоящем DOM:

```
npm install jsdom
node docs/assets/render_check.js
```

Он смотрит на то, ради чего страница есть: нарисовались ли карточки, зажглись ли
связи, работает ли переход по кнопке, собирается ли конфиг имён. В общий
`tests/run.sh` не входит намеренно — тому нужен только docker, а здесь нужен
node.

## Самопроверка сборщика

Сборщик отказывается записывать карту, если разбор роутера развалился: нет
корневых экранов, от главного меню доступно меньше полусотни экранов или больше
десятой части кнопок осталась без ветки. Пустая карта выглядела бы не как
поломка, а как «ну вот такая теперь архитектура», — и это худший исход.

Сейчас: **246 экранов, 833 кнопки**, от главного меню доступно 175, без ветки —
одна (её `callback_data` подставляется на лету).
