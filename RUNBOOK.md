# Что делать, когда сломалось

Написано для человека, который знает Linux и docker, но этот проект видит
впервые. Без владельца. Порядок — от «скорее всего это» к «скорее всего не
это»; делайте сверху вниз и останавливайтесь, когда заработало.

Правило одно: **сначала посмотреть, потом чинить.** Почти всё здесь чинится
само, и торопливое вмешательство чаще мешает, чем помогает.

> **Адреса в примерах ненастоящие.** `203.0.113.10` и `198.51.100.20` — из
> диапазонов, выделенных под примеры. Репозиторий открытый, и настоящие адреса
> в нём — это готовая карта: вот машина, вот порт, вот root. Свои подставьте
> сами; они есть в панели бота и в вашем `~/.ssh/config`. Удобнее всего задать
> их один раз на сессию, тогда команды ниже работают как есть:
>
>     RU=<адрес мастера>; DE=<адрес выхода>
>     ssh -p 23232 root@$RU

## Что вообще есть

Две машины. **Мастер** в России — на нём всё: туннель, база, Telegram-бот,
панель управления. **Выход** в Германии — через него уходит трафик, который не
должен идти напрямую. Мастер ходит в Германию по своему же туннелю.

| | Мастер (РФ) | Выход (Германия) |
|---|---|---|
| адрес | 203.0.113.10 | 198.51.100.20 |
| вход | `ssh -p 23232 root@…` | то же |
| проект | `/root/vpn_awg_2_VPS` | то же |
| нода | `VPS_RU/` | `VPS_DE/` |
| контейнеры | `vpn_wireguard`, `vpn_bot`, `vpn_db` | `de_vpn_agent` |
| демон команд | `vpn-updater` | `de-agent-updater` |
| сторож | `vpn-watchdog` | `vpn-watchdog` |
| уборка | `vpn-cleanup.timer`, вс ~05:00 | то же |

Внутри туннеля мастер — `10.13.13.1`, Германия — `10.13.13.254`, люди — с
`10.13.13.2` и дальше.

Бот управляет узлом не напрямую, а через файлы-метки в
`VPS_RU/volumes/flags/`. Демон хоста проверяет их раз в пять секунд:
`do_update`, `do_reboot`, `do_audit`, `do_restart_wg`, `do_cleanup`,
`do_public_sub`. Положить метку руками — законный способ сделать то же, что
делает кнопка.

## Обновить обе ноды одной командой

Обычно это делается кнопкой в боте. Когда бот недоступен — вот то же самое
руками, по одной строке на ноду:

    ssh -p 23232 root@203.0.113.10 'touch /root/vpn_awg_2_VPS/VPS_RU/volumes/flags/do_update'
    ssh -p 23232 root@198.51.100.20   'touch /root/vpn_awg_2_VPS/VPS_DE/volumes/flags/do_update'

Демон подхватит метку за пять секунд и запустит `deploy.sh`: тот сам стянет код,
пересоберёт образы и откатится на прошлую версию, если ядро маршрутизации после
сборки не отвечает. Сборка идёт три-пять минут — ответа ждать не надо.

**Порядок важен только в одну сторону:** мастер первым. Он раскладывает
настройки на обе ноды, и Германия, обновившаяся раньше, просто подождёт.

Посмотреть, чем кончилось:

    ssh -p 23232 root@203.0.113.10 'docker logs --tail 40 vpn_bot; docker images | grep vpn-'

Версия в теге образа — она же и есть та, что реально крутится.

## Сертификат узла

Нужен странице отказа: с ним она открывается без предупреждения браузера. Лежит
в `VPS_RU/volumes/certs/fullchain.pem`; нет файла — страница работает на
самоподписанном, и это не поломка.

    bash scripts/public_sub.sh status     # есть? до какого числа?
    bash scripts/public_sub.sh renew      # продлить сейчас
    bash scripts/public_sub.sh off        # убрать совсем

На IP-адрес сертификат живёт неделю, продлевает его `vpn-subcert.timer`
дважды в сутки:

    systemctl list-timers vpn-subcert
    tail -20 /tmp/certbot-renew.log

## Сначала — просто посмотреть

    ssh -p 23232 root@203.0.113.10
    cd /root/vpn_awg_2_VPS
    docker ps                       # что поднято
    systemctl status vpn-watchdog   # сторож жив?
    docker logs --tail 50 vpn_bot
    docker logs --tail 50 vpn_wireguard

Это ничего не меняет. Если руки чешутся — всё равно сначала это.

## «Ни у кого не работает интернет»

**1. Проверьте туннель.**

    docker exec vpn_wireguard wg show wg0

Пусто или интерфейса нет — перезапустите ядро туннеля меткой, а не руками:

    touch VPS_RU/volumes/flags/do_restart_wg

Демон подхватит её за пять секунд. Ждать до минуты.

**2. Проверьте, не Германия ли это.** Если туннель цел, но людям не открываются
сайты — скорее всего лёг выход:

    docker exec vpn_wireguard wg show wg0 | grep -A3 10.13.13.254
    curl -s --max-time 5 http://10.13.13.254:8000/api/health

Если Германия молчит, трафик должен уйти напрямую — у мастера есть режим
обхода. Он включается сам, но можно и руками, из бота: «Сервер Германии» →
проверить состояние.

**3. Сторож.** Он лечит узел сам, поэтапно, и обычно успевает раньше человека.

    journalctl -u vpn-watchdog -n 100 --no-pager

Если в журнале видно, что он ходит по кругу и перезапускает одно и то же —
вот это и есть настоящая беда, читайте, на чём он спотыкается.

## «Бот не отвечает»

Бот — это только управление. **Люди при этом сидят в интернете нормально**,
туннель от бота не зависит. Не торопитесь.

    docker logs --tail 100 vpn_bot
    docker compose -f VPS_RU/docker-compose.yml restart vpn_bot

Не поднимается — почти всегда база:

    docker exec vpn_db pg_isready -U vpn_admin -d vpndb

## «Обновление сломало прод»

Само не должно: деплой перед работой делает бэкап базы, а после — проверку
здоровья, и при неудаче откатывается на прошлый коммит сам. Если всё-таки:

    cd /root/vpn_awg_2_VPS
    git log --oneline -5
    git reset --hard <хеш рабочей версии>
    cd VPS_RU && docker compose up -d --build

Бэкапы базы: `VPS_RU/volumes/backups/`, самый свежий —
`backup_latest.tar.gz`. Восстановление описано в `Readme.md`.

## Проверить всё разом

В боте: «Сервер России» → «Аудит мастера». Придёт файлом отчёт на полсотни
проверок, включая сверку базы с тем, что реально стоит на узле. То же самое
руками:

    touch VPS_RU/volumes/flags/do_audit
    sleep 60 && cat VPS_RU/volumes/flags/audit_report.json

Отдельно сверка базы с узлом — она показывает расхождения, которых не видно
никак иначе (человек есть в базе, а на узле его нет; на узле есть доступ,
которого никто не выдавал):

    docker exec vpn_bot python3 /app/tests/contract/node_contract.py

## Чего делать не надо

- **Не чистить пакеты руками.** Есть сборщик: `bash scripts/gc.sh`. Он
  проверяет зависимости и отказывается трогать то, что тянет за собой ядро.
  Посмотреть, ничего не удаляя: `bash scripts/gc.sh --показать`.
- **Не править iptables руками.** Правила ставит `VPS_RU/ru_wg_api/api.py` при
  старте контейнера, и при следующем перезапуске ваша правка исчезнет. Менять
  надо в коде.
- **Не удалять ничего из `volumes/`.** Там база, конфиги и бэкапы. Именованные
  тома докера проекту не принадлежат — всё в bind-mount.
- **Не перезагружать обе ноды разом.**

## Перед тем как отправлять свои правки
